# Platform Restructure Plan

## Direction

The project should be a multimodal knowledge and memory platform first.

Deep research and report generation remain important, but they are applications on top of
the core platform rather than the whole product.

## New Product Shape

```text
sources and connectors
  -> assets
  -> shallow knowledge files
  -> graph records
  -> memory records
  -> agent applications
```

The same project knowledge base should support:

- chat and Q&A
- local document understanding
- source connector ingestion
- progressive source deepening
- memory from user-agent conversations
- deep research
- report generation and editing
- wiki/briefing/export workflows later

## Core Concepts

### Assets

Original or generated bytes stored in object storage.

Examples:

- uploaded PDFs, images, spreadsheets, docs, code archives
- fetched web pages
- Slack thread snapshots
- GitHub issue/repo snapshots
- generated reports, charts, tables, exports

### Knowledge Files

Agent-readable markdown or text files that summarize or organize knowledge.

Examples:

- source card
- topic card
- repository card
- image card
- research map
- report section
- scratch note

### Knowledge Graph

Structured projection over assets and knowledge files.

Examples:

- topics
- entities
- claims
- facts
- source chunks
- code symbols
- citations
- contradictions
- relationships across sources

The graph returns mechanical results. The agent decides relevance.

The graph is evidence-first. Extracted claims and relationships enter a candidate layer
before promotion, and every promoted semantic record must retain exact source provenance,
extraction version, scope, and temporal status. Vector and optional graph databases are
rebuildable projections of stable Postgres-owned identities. See
[knowledge-graph-design.md](knowledge-graph-design.md).

### Memory

Durable lessons from user-agent interaction.

Examples:

- user preferences
- user corrections
- project decisions
- source quality notes
- terminology definitions
- reusable conclusions
- explicit "remember this" instructions

Memory should link back to messages, assets, knowledge files, graph nodes, or chunks when
possible.

### Source Connectors

External systems that feed the knowledge base.

Initial candidates:

- local uploads
- web pages and crawled sites
- Slack and team communication
- GitHub repositories, issues, and pull requests
- Notion, Google Drive, and other knowledge apps
- Linear/Jira work management
- email/calendar later
- databases and internal APIs later

Every connector should preserve provenance and permissions.

See [source-connectors.md](source-connectors.md) for the detailed connector strategy.

### Agent Applications

User-facing workflows built on the same knowledge and memory substrate.

Initial applications:

- chat over knowledge
- document Q&A
- deep research
- report generation
- report editing

Later applications:

- wiki generation
- meeting/Slack summaries
- decision tracking
- codebase understanding
- source comparison
- export/publishing workflows

## Revised V1 Build Order

1. Shared platform contracts
   - projects
   - knowledge scopes
   - assets
   - knowledge files
   - graph records
   - graph schema registry and extraction candidates
   - exact source ranges, entity resolution, and projection identities
   - memory records
   - source connectors
   - agent tasks
   - product events

2. Runtime foundation
   - API
   - worker
   - queue
   - Postgres migrations
   - object storage
   - WebSocket event stream
   - Docker Compose
   - CI

3. Local upload ingestion
   - asset upload
   - shallow source cards
   - initial graph records
   - source ranges/chunks
   - candidate validation and promotion
   - ingestion and provenance evaluation fixtures
   - ingestion events

4. Chat over knowledge
   - conversation persistence
   - context assembly
   - graph/file retrieval
   - query routing between lexical, vector, and graph strategies
   - auditable retrieval result sets
   - citation-backed answers
   - source deepening when needed

5. Memory layer
   - memory candidates from chat
   - user approval for sensitive/high-impact memories
   - memory retrieval during future turns
   - memory links to messages and source records

6. First connector
   - choose web URLs, GitHub, or Slack
   - sync source records into assets
   - create shallow knowledge files and graph records
   - support incremental sync

7. Deep research application
   - planner
   - researcher subagents
   - Search as Code
   - deeper source inspection
   - answer/brief/report outline outputs

8. Report application
   - report workspace
   - Markdown section editor
   - evidence/assets/graph/memory panels
   - visual asset blocks
   - citations and exports

## Issue Restructure Needed

The existing GitHub issues are still useful, but several should be renamed or regrouped:

- M1 should become "Knowledge Platform Spine".
- M3 should become "Ingestion, Tools, And Connectors".
- Add a new milestone for "Knowledge And Memory Workflow".
- Move deep research/report issues behind the platform foundation.
- Add issues for memory records, memory extraction, memory approval, source connector
  contracts, and chat over knowledge.
- Keep report/editor issues, but treat them as an application layer.

## Open Decisions

- Which connector should come first after local uploads and web URLs: GitHub, Slack,
  Notion, or Google Drive?
- Should V1 memory default to project-local only, or include user-global memory?
- Which memory types require user approval?
- Should `product_events` replace `research_events` immediately, or should we keep both
  during the transition?
- Should the central UI be called a knowledge workspace, project workspace, or something
  more specific?
